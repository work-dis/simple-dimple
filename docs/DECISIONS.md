# Decisions

Этот документ фиксирует ключевые решения по проекту и их мотивацию.

Он нужен, чтобы потом не спорить заново об уже принятых базовых направлениях и не терять контекст, почему мы пошли именно этим путем.

## Decision 001

Дата: `2026-07-06`

Тема: основной клиент проекта строим как `PWA-first`

Решение:

- сначала делаем основной пользовательский клиент как `PWA`
- после стабилизации UX готовим упаковку в `Android` и `iOS`

Почему:

- это дает быстрый цикл проверки интерфейса и логики
- это не раздувает ранний этап нативной инфраструктурой
- это соответствует продуктовой цели с простым mobile-first UX

Последствия:

- приоритет у web-клиента
- нативная упаковка идет следующим этапом, а не первым

## Decision 002

Дата: `2026-07-06`

Тема: сначала поднимаем два отдельных dev-сервера

Решение:

- backend и frontend запускаются как два независимых локальных сервера
- frontend связывается с backend через dev proxy

Почему:

- так быстрее начать проверять UX и прикладную логику
- так проще независимо развивать клиент и API
- это удобный стартовый стенд до появления полной infra-схемы

Последствия:

- локальная разработка идет через `5173` и `8080`
- текущий контур пока не равен будущей production-инфраструктуре

## Decision 003

Дата: `2026-07-06`

Тема: пользовательский UX должен оставаться предельно простым

Решение:

- главный экран строим вокруг одной основной кнопки `Подключить`
- допускаем максимум один дополнительный повседневный сценарий вроде `Сервер` или `Аккаунт`

Почему:

- это центральная продуктовая идея проекта
- это не дает интерфейсу скатиться в dashboard-style продукт
- это соответствует mobile-first сценарию

Последствия:

- технические детали не должны лезть на главный экран
- admin и служебные возможности должны жить отдельно

## Decision 004

Дата: `2026-07-06`

Тема: стартуем без раннего усложнения инфраструктуры

Решение:

- на первом этапе не подключаем сразу `PostgreSQL`, `Prisma`, `Xray` и `Capacitor`
- вместо этого делаем минимальный рабочий стенд для быстрой проверки основного сценария

Почему:

- сначала нужно проверить главный пользовательский поток
- раннее инфраструктурное усложнение замедляет продуктовую итерацию
- мы хотим двигаться поэтапно и осознанно

Последствия:

- backend state пока хранится в памяти
- текущий стенд временный и будет эволюционировать
- следующий шаг уже включает переход к persistent state

## Decision 005

Дата: `2026-07-06`

Тема: выбор сервера не должен жить на главном экране

Решение:

- экран `Home` оставляем только для статуса и главного действия `Подключить`
- выбор сервера переносим в отдельный экран `Server`
- `Account` добавляем позже отдельным шагом, не ломая простоту `Home`

Почему:

- это сохраняет главный сценарий быстрым и понятным
- это соответствует roadmap с максимум двумя действиями на главной поверхности
- это не дает интерфейсу снова скатиться в список технических карточек

Последствия:

- `frontend` строится как набор простых пользовательских экранов, а не один перегруженный экран
- серверный выбор остается доступным, но не мешает ежедневному подключению
- дальнейшее добавление `Account` должно сохранять ту же дисциплину простоты

## Decision 006

Дата: `2026-07-06`

Тема: `Account` должен быть отдельным служебным экраном

Решение:

- пользовательские данные, подписка и выход живут на отдельном экране `Account`
- `Account` не должен конкурировать с главной кнопкой подключения
- главный экран остается про подключение, а не про управление профилем

Почему:

- это удерживает основной сценарий быстрым
- это завершает базовую трехэкранную схему `Home / Server / Account`
- это помогает не смешивать продуктовый UX и служебные данные

Последствия:

- дальнейшая auth-логика подключается через `Account`, а не через перегрузку `Home`
- данные аккаунта можно развивать независимо от подключения и выбора сервера

## Decision 007

Дата: `2026-07-06`

Тема: данные `Account` должны приходить из backend API

Решение:

- экран `Account` больше не держит account summary как фронтенд-константу
- даже на dev-этапе account-данные приходят через отдельный backend endpoint
- auth и subscriptions дальше наращиваются вокруг этого серверного контракта

Почему:

- это убирает лишнюю фиктивную логику из UI
- это делает `Account` частью реального клиент-серверного потока
- это позволяет эволюционировать к `users/auth/subscriptions` без переделки UX-слоя

Последствия:

- backend API постепенно становится источником истины не только для сессии подключения, но и для пользовательских данных
- фронтенд можно развивать дальше без возврата к локальным account-заглушкам

## Decision 008

Дата: `2026-07-06`

Тема: первые изменения пользовательских данных должны идти через backend

Решение:

- редактирование контакта на экране `Account` проходит через backend endpoint
- даже простой write-flow не держим только во фронтенд-состоянии
- UI остается минимальным: одно поле и одно понятное действие

Почему:

- это помогает рано зафиксировать правильный контракт между UI и сервером
- это приближает dev-стенд к реальной модели `user/account`
- это дает полезный шаг вперед без преждевременного внедрения полной auth-системы

Последствия:

- дальнейшие account-поля логично добавлять через тот же API-подход
- фронтенд не должен накапливать фиктивные edit-flow без серверной поддержки

## Decision 009

Дата: `2026-07-06`

Тема: `Account` должен опираться на явные сущности, а не на плоскую сводку

Решение:

- в backend выделяем `user`, `subscription` и `devices` как отдельные части account-модели
- frontend `Account` читает и редактирует данные уже в этой структуре
- даже до БД и auth держим shape данных близким к будущей реальной модели

Почему:

- это упростит последующий переход к persistent storage
- это делает auth и subscription-логику естественным продолжением, а не переделкой
- это удерживает проект в движении по roadmap без большого инфраструктурного прыжка

Последствия:

- следующий крупный шаг логично делать вокруг persistence
- новые account-возможности должны добавляться вокруг этих сущностей, а не через новые плоские заглушки

## Decision 010

Дата: `2026-07-06`

Тема: до БД используем файловое dev-хранилище

Решение:

- текущий backend сохраняет `session` и `account` в локальный файл `backend/data/app-state.json`
- это временный dev-слой между pure in-memory состоянием и настоящей БД
- запись происходит после изменений пользовательских и session-данных

Почему:

- это убирает сброс состояния при рестарте backend
- это позволяет двигаться по плану без преждевременного подключения полной БД-инфраструктуры
- это делает следующий переход к БД более осмысленным, потому что граница persistence уже выделена

Последствия:

- локальный dev-стенд стал стабильнее и ближе к реальному поведению
- следующим storage-шагом должна быть уже БД, а не новые in-memory усложнения

## Decision 011

Дата: `2026-07-06`

Тема: в `PostgreSQL` логически разделяем `core`, `telemetry`, `analytics` и `ops`

Решение:

- основной production storage планируем на `PostgreSQL`
- клиентские сущности, сырые client reports, агрегаты ranking и ops/audit разделяем по отдельным схемам
- на старте допускаем одну физическую БД, но не смешиваем домены данных в одной бесформенной модели

Почему:

- пользовательские данные и network telemetry имеют разный смысл, разные retention policy и разные риски
- это делает будущий рост более управляемым
- это позволяет позже вынести telemetry физически отдельно, если нагрузка или privacy-требования вырастут

Последствия:

- `clients` и `reports` проектируются отдельно уже на этапе схемы
- migration к БД должна начинаться с `core`, а telemetry и analytics добавляться как отдельные слои

## Decision 012

Дата: `2026-07-06`

Тема: вводим `Prisma + PostgreSQL` через гибридный storage-слой

Решение:

- backend получает `Prisma`-каркас и initial migration уже сейчас
- runtime использует режим `auto`: при наличии `DATABASE_URL` идем в `PostgreSQL`, без него остаемся на file-backed store
- `session` и `account` становятся первыми сущностями, для которых готов DB-backed store

Почему:

- это позволяет начать реальную DB-интеграцию без остановки локальной разработки
- это снижает риск большого одномоментного перехода
- это даёт понятную точку для следующего шага: поднять реальную БД и отключить fallback

Последствия:

- storage-слой теперь выделен явно, а не зашит прямо в сервер
- следующая storage-задача уже не “выбрать БД”, а “подключить и применить migration к реальному PostgreSQL”

## Decision 013

Дата: `2026-07-06`

Тема: переводим dev runtime на обязательный `PostgreSQL`

Решение:

- локальная БД поднимается через `docker compose`
- backend больше не использует file-backed fallback для `session` и `account`
- `DATABASE_URL` становится обязательным runtime-параметром

Почему:

- это убирает расхождение между CLI migration flow и реальным runtime
- это делает dev-среду ближе к тому storage-контракту, с которым дальше будут строиться auth и server-domain сущности
- это снижает риск того, что часть изменений тестируется на файле, а часть на БД

Последствия:

- локальный запуск теперь начинается с `db:up` и `db:migrate`
- ошибки подключения к БД теперь проявляются сразу на старте backend, а не маскируются fallback-путём

## Decision 014

Дата: `2026-07-06`

Тема: закладываем auth foundation через `login/password` в БД

Решение:

Последствия:

- dev-стенд теперь проверяет не только `account` API, но и auth endpoints

|## Decision 015

Дата: `2026-07-06`

Тема: рефакторинг и hardening хранилища состояний

Решение:

- `seedDefaultData()` вызывается один раз после создания store, а не в каждом методе чтения/записи
- `recomputeAnalyticsForFingerprint()` удаляет ranking только для текущего time bucket (`expiresAt: bucketEnd`) вместо полной очистки всей истории fingerprint
- auth-сессии создаются с `randomUUID()`, а не с фиксированным `id = "primary"`; `readState()` ищет последнюю активную сессию через `findFirst`, а не `findUnique` по жёсткому id
- добавлен `writeSession(session)` — метод, обновляющий только `AppSession`, без перезаписи `user`, `subscription`, `device`, `auth` и ranking-данных
- добавлен rate limiter (`@fastify/rate-limit`, 100 req/min глобально)

Почему:

- inline-вызов `seedDefaultData()` в каждом методе давал 7 лишних DB-запросов на каждый API-вызов
- удаление всей истории ranking при пересчёте одного bucket — это потеря данных для трендов и аналитики
- фиксированное id `"primary"` не позволяло поддерживать несколько активных сессий с разных устройств
- `writeState()` перезаписывал всю вложенную структуру, хотя connect/disconnect/server-select меняют только `AppSession`
- у сервера не было базовой защиты от brute-force даже на dev-этапе

Последствия:

- хранилище стало эффективнее: seed — 1 раз, ranking — точечное удаление, writeSession — один upsert
- заложена multi-device поддержка: каждая сессия имеет уникальный UUID; `readState` выбирает последнюю активную
- rate limiter даёт baseline-защиту; при появлении login/register endpoints его нужно будет точечно ужесточить
- все изменения совместимы с текущей Prisma-схемой и не требуют миграции

## Decision: policy-engine живет в отдельном модуле, а не внутри HTTP-роутов

Тема: выделение decision logic shortlist/assignment из transport-слоя API

Решение:

- `normalizeTelemetryContext()`, `hasTelemetryContext()` и `buildRoutePolicy()` вынесены в отдельный модуль `backend/src/route-policy.ts`
- [backend/src/server.ts](/Users/miko/Documents/simple-dimple/backend/src/server.ts:1) теперь только собирает network context, запрашивает servers/assignment и возвращает policy-ответ
- `routePolicy` стал самостоятельным runtime-слоем между ranking-данными и API-контрактом

Почему:

- shortlist и assignment reasoning — это доменная decision logic, а не обязанность HTTP-роутов
- следующий шаг с persisted `last-known-good route` и `decision trace` проще и безопаснее делать поверх отдельного модуля
- так легче добавлять точечные тесты и переиспользование в других потоках, не привязанных к одному endpoint

Последствия:

- роуты стали тоньше и лучше разделяют orchestration и policy
- следующий инкремент roadmap теперь логично строить вокруг `route-policy`, а не вокруг случайных условных блоков в `server.ts`
- архитектура стала ближе к shared-core варианту из roadmap, без смены текущего API-контракта

## Decision: last-known-good хранится отдельно от assignment

Тема: persisted success-state для policy-engine

Решение:

- вводим отдельную таблицу `LastKnownGoodRoute`, а не пытаемся выводить “последний рабочий маршрут” из `UserEndpointAssignment`
- successful `connect` пишет отдельную запись с `userId`, `deviceId`, `networkFingerprintId`, `endpointId`, `sourceAssignmentReason`, `lastSucceededAt` и `expiresAt`
- policy-engine сначала читает `last-known-good` для текущего сетевого отпечатка, затем при необходимости падает обратно на ranking/baseline flow

Почему:

- assignment фиксирует решение control plane, но не доказывает, что маршрут действительно пережил успешное подключение
- persisted success-state проще валидировать по TTL и coarse network context
- это убирает смешение двух разных смыслов: “что выдали” и “что реально сработало”

Последствия:

- policy-engine теперь опирается на более честный источник `last_known_good`
- появилась база для следующего шага с `decision trace` и более умной cross-network fallback логикой
- схема БД стала ближе к модели из `NETWORK_INTELLIGENCE`, но без усложнения внешнего UX

## Decision: decision trace делаем компактным и internal-only

Тема: explainability для policy-engine без нового пользовательского слоя

Решение:

- `routePolicy` возвращает компактный `trace` с полями `selectedBy`, `usedManualOverride`, `usedLastKnownGood`, `usedNetworkRanking` и `fallbackTier`
- trace живет в runtime/API-контракте, но не требует отдельной БД-схемы
- главная поверхность UX не меняется; служебная мета может показываться только на secondary-экранах

Почему:

- нам нужна инженерная прозрачность policy-решения, но не нужен новый diagnostic UI на главном экране
- lightweight trace закрывает debugging и future feedback-loop без лишней архитектурной тяжести

Последствия:

- shortlist-решения стали наблюдаемыми
- следующий шаг roadmap можно делать вокруг diversity/failure-domain hardening, а не вокруг догадок о том, что выбрал policy-engine

## Decision: shortlist diversity усиливаем по provider / ASN / IP, а не только по transport

Тема: failure-domain hardening для policy-engine

Решение:

- в runtime `ServerOption` и `RoutePolicyCandidate` добавлены `asn` и `ipAddress`
- diagnostic fallback теперь предпочитает другой `IP` и/или другой transport, а diversity fallback старается вынести кандидатов в другой `provider` или `ASN`
- `routePolicy.trace` считает, насколько реально получился разнос shortlist по failure domains

Почему:

- “другой маршрут” внутри того же провайдера и того же `ASN` часто не является настоящим fallback
- без явных failure-domain правил shortlist может выглядеть разным, но иметь одну и ту же точку отказа

Последствия:

- shortlist стал ближе к требованиям `NETWORK_INTELLIGENCE`
- следующий шаг логично смещается к feedback-loop для деградировавших маршрутов, а не к дальнейшему косметическому reshuffle shortlist

## Decision: feedback-loop для деградировавших маршрутов строим поверх probe_reports

Тема: быстрый runtime-avoidance проблемных endpoints без новой persistent схемы

Решение:

- не вводим отдельную таблицу suppression/penalty на этом этапе
- policy-engine читает свежие `probe_reports` для текущего `networkFingerprint`
- endpoint считается временно деградировавшим, если у него есть серия свежих неуспешных результатов без последующего success
- такой endpoint по возможности исключается из основного candidate pool, но emergency fallback все еще может до него дойти

Почему:

- это самый дешёвый способ замкнуть feedback-loop на уже существующей telemetry
- мы получаем реакцию на свежую деградацию без новой миграции и без отдельного feedback API

Последствия:

- policy-engine быстрее уходит от недавно упавших маршрутов
- следующий этап логично переводится в сторону более точного scoring/penalty model, если простого avoid-list станет недостаточно

## Decision 017

Дата: `2026-07-06`

Тема: разбиение монолитного state-store.ts на доменные модули

Решение:

- `state-store.ts` (2406 строк) разбит на 6 модулей в `backend/src/store/`:
  - `utils.ts` — чистые функции без Prisma (хеши, мапперы, ranking score, ошибки)
  - `shared.ts` — Prisma-зависимые хелперы, общие для нескольких модулей
  - `auth.ts` — login, register, challenge/verify, logout
  - `session.ts` — readState, writeState, writeSession, assignEndpoint, lastKnownGoodRoute
  - `telemetry.ts` — submitProbeReport, submitFeedback, getHealthSnapshots, getRankings
  - `admin.ts` — listAdminUsers, updateAdmin, getOpsSummary
- `state-store.ts` (82 строки) остаётся фасадом — импортирует модули и композирует их
- Каждый модуль экспортирует фабрику `createXxxStore(prisma)`, фасад вызывает все фабрики с одним `PrismaClient`
- Signalты методов унифицированы под объектный стиль, адаптированы вызовы в `server.ts`

Почему:

- Монолит 2406 строк сделать невозможно читать и ревьюить — любой багфикс требует пролистывать весь файл
- auth, session, telemetry и admin — разные домены с разными темпами изменений
- utils без Prisma-зависимости можно покрыть тестами без поднятия БД
- Добавление нового домена теперь — один файл и одна строка в фасаде
- Переименование методов заодно привело сигнатуры к единому стилю (объекты-аргументы)

Последствия:

- Каждый модуль можно читать и менять изолированно
- server.ts вызывает store через единый фасад — импорты не менялись
- HTTP-контракты API не изменились
- Следующий шаг: разобрать frontend/App.tsx (1700 строк) — та же проблема

## Decision 018

Дата: `2026-07-07`

Тема: вынос orchestration-логики из frontend/App.tsx в доменные hooks

Решение:

- `frontend/src/App.tsx` остается экранным shell-компонентом и больше не держит внутри все API-вызовы
- `auth/account` состояние и handlers вынесены в `frontend/src/hooks/useAuthAccount.ts`
- `route/session/connect` flow вынесен в `frontend/src/hooks/useRouteSession.ts`
- admin и ops загрузка вынесены в отдельные hooks `useAdminUsers.ts` и `useRouteDecisionOps.ts`
- network context и best-effort telemetry submit вынесены в `frontend/src/lib/network.ts`

Почему:

- экранные компоненты уже были выделены, но orchestration-слой все еще жил в одном файле и смешивал несколько доменов
- auth, routing, admin и ops меняются независимо и не должны конкурировать за место в `App.tsx`
- вынесенные hooks проще тестировать, читать и дорабатывать без риска случайно затронуть соседний flow

Последствия:

- `App.tsx` стал тоньше и теперь в основном занимается navigation и сборкой экранов
- поведение API и props экранов в основном сохранены, поэтому refactor не требует переписывать UI-компоненты
- следующий frontend-шаг уже логичнее делать вокруг локальных тестов hooks или более мелких screen-container границ, а не вокруг нового монолита

## Decision 019

Дата: `2026-07-07`

Тема: Prisma generation в CI выносим в отдельный последовательный шаг

Решение:

- добавляем GitHub Actions workflow `.github/workflows/ci.yml`
- CI сначала отдельно выполняет `npm run prisma:generate --workspace backend`
- после этого в том же job последовательно идут `prisma migrate deploy`, checks, backend tests и build
- для CI добавлены отдельные команды `npm run ci:check` и `npm run ci:build`, которые не запускают `prisma generate` повторно

Почему:

- локальные `backend`-скрипты `check` и `build` оба пересоздают `src/generated/prisma`
- при параллельном запуске в одном workspace это создает гонку и может приводить к `ENOENT` внутри generated client
- отдельный generate-step делает pipeline предсказуемым и не меняет привычный локальный DX

Последствия:

- CI проверяет тот же проектовый контур, но без конкуренции за Prisma output directory
- локальные команды `npm run check` и `npm run build` остаются удобными для одиночного запуска
- если позже захотим упростить локальные скрипты, это можно будет делать отдельно от CI
